三、系统分层防御体系（分阶段实施）
设计原则：项目起步阶段用户量极少，不盲目引入复杂中间件。但随着用户增长，系统架构按以下三个阶段平滑演进，代码无需重写，只需调整部署方式和新增配置。

3.1 阶段一：MVP上线期（当前 → 用户量 < 1000）
目标：快速上线，功能可用，成本最低。

部署架构：单机部署（一台阿里云轻量应用服务器，2核4G）。

组件	部署方式	说明
MySQL	安装在服务器本地	数据存储
Redis	安装在服务器本地	会话管理 + 基础缓存
Spring Boot	运行 java -jar	后端服务
Nginx	安装在服务器本地	托管前端静态文件 + 反向代理
安卓App	用户手机	通过API访问后端
必须做好的基础工作（为后续扩展预留接口）：

事项	具体做法	目的
Session存Redis	用户登录状态存Redis，不存内存Map	后续加多台服务器时用户不丢失登录态
文件存OSS	用户头像、社区图片直传阿里云OSS，数据库只存URL	后续加服务器时图片不丢失
配置外置化	数据库IP、Redis IP等用环境变量注入	换服务器只改配置，不改代码
统一返回格式	{ code: 200, message: 'success', data: ... }	前后端联调规范
日志记录	使用SLF4J + Logback，按日切割	出问题时快速定位
数据库连接池配置示例（application.yml）：

yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10          # 最大连接数（起步阶段够用）
      minimum-idle: 5
      connection-timeout: 30000
      idle-timeout: 600000
      max-lifetime: 1800000
事务管理：使用Spring @Transactional 注解管理本地事务，确保数据一致性。

3.2 阶段二：用户增长期（用户量 1000 ~ 50000）
触发条件：日活持续增长，单机CPU/内存告警，或数据库连接数不足。

架构升级（代码无需改动）：

新增组件	作用	部署方式
第二台服务器	部署后端应用，实现负载均衡	新增一台阿里云服务器
Nginx负载均衡	将请求分发到两台后端服务器	配置 upstream 反向代理集群
数据库独立部署	将MySQL迁移到单独服务器	原服务器仅跑后端，数据库独立
Redis独立部署	将Redis迁移到单独服务器	保证多台后端共享同一缓存
此阶段代码改动量：0行。只需修改配置文件中的IP地址，重启服务即可。

新增技术关注点：

开始关注慢SQL，使用MySQL EXPLAIN 分析查询计划，逐步添加索引

引入Caffeine本地缓存，将字典表、配置项等极少变更的数据缓存在应用内存中

接入阿里云应用实时监控服务（ARMS） 或 Prometheus + Grafana，监控服务器状态

3.3 阶段三：大规模并发期（用户量 > 50000）
触发条件：QPS持续升高，数据库成为瓶颈，或出现缓存穿透/雪崩风险。

架构升级（代码按需微调，非重写）：

新增组件	作用	说明
Redis集群	高可用缓存	主从+哨兵模式，防止单点故障
读写分离	主库写、从库读	使用ShardingSphere-JDBC或MySQL原生主从
消息队列（RocketMQ）	异步解耦、削峰填谷	用于社区发帖通知、路线生成结果推送等非实时场景
分库分表	水平拆分数据	用户表、路线表按ID取模分库分表
API网关（Spring Cloud Gateway）	统一路由、限流熔断	配合 Sentinel 实现流量控制，防止系统过载
此阶段代码改动量：少量。主要是在关键接口上增加 Sentinel 的 @SentinelResource 注解配置降级/熔断规则；将耗时操作改为通过消息队列异步处理。

限流熔断策略（以高德地图API调用为例）：

高德地图SDK的POI检索接口有调用频率限制（免费版QPS上限约50）。使用Sentinel配置限流规则，超出部分返回友好提示“查询过于频繁，请稍后再试”，避免因第三方接口限流导致整个服务不可用。


四、App 页面功能设计
4.1 全局基础架构
底部导航栏（4个Tab）：主页（罗盘图标）、行程（路线图标）、社区（聊天气泡图标）、我的（人像图标）。

全局定位：进入App强制获取一次位置（可手动切换城市），所有“周边”推荐基于此经纬度。

通用组件：顶部状态栏适配深色/浅色模式；加载时采用“骨架屏”提升流畅感。

4.2 Tab 1：主页（探索）
设计理念：快速触达用户当下的即时需求，同时用“榜单”和“天气”建立开启App的仪式感。

页面从上到下布局：

顶部定位栏 + 搜索框：

左侧显示当前城市（如“广州市 · 晴 28°”）。

中间是搜索框（占位词：“想去哪儿？搜景点或美食”）。

右侧核心按钮：“✨ AI魔法棒”（一键唤起AI对话生成器，无需跳转Tab2，浮层弹出）。

快捷分类入口（横向滚动）：

图标区：🏞️ 景点 | 🍜 美食 | 🏨 住宿 | 🚗 周边游 | 📸 拍照圣地。

今日天气与出行建议（卡片）：

显示今日温度区间、降雨概率、风力。

附带一句AI生成的贴心文案。

“附近正在热玩”双列瀑布流（信息流）：

基于LBS展示周边1-5公里内的热门景点/店铺。

每张卡片显示：首图、名称、评分、距离、当前拥挤度/排队情况。

城市必玩榜单（横向滑动）：

“本地人私藏TOP5”、“情侣约会圣地TOP3”、“亲子遛娃TOP3”（初期由运营配置，后期由社区数据自动生成）。

4.3 Tab 2：行程（核心）
设计理念：用户的核心价值所在——高效管理旅行路线。以时间轴和状态为中心。

页面从上到下布局：

顶部状态切换器（胶囊式分段控件）：

“进行中” / “已保存” / “已结束”。

默认展示“进行中”/“已保存”的卡片列表：

每张行程卡片摘要：封面图、行程名称、日期、景点总数、总预估步行时长。

卡片右下角按钮：“继续规划”或“开始导航概览”。

右下角悬浮突出按钮（FAB）：“➕ 生成新路线”。

点击“➕”后的AI路线生成器：

步骤1（表单化输入）：目的地、游玩天数（1-5天）、同行人（独自/情侣/带娃/带长辈/宠物）、偏好、每日预算区间。

步骤2（生成过程）：AI思考动画（3-5秒），调用大模型API生成路线。

步骤3（结果展示）：可拖拽排序的每日时间轴。

时间卡片：时间段 + 地点名称 + 交通建议。

交互亮点：用户长按拖动调整顺序，AI自动重新计算衔接时间和总时长。

每个景点卡片旁有“🗺️ 查看地图”按钮，点击跳转至第三方地图（高德/百度）进行导航。

4.4 Tab 3：社区（灵感）
设计理念：路线是“完整的规划”，社区是“灵光一闪的碎片”。核心突出 “本地人信任感”。

页面从上到下布局：

顶部城市筛选器：默认显示当前定位城市，可下拉切换全国热门城市。

内容分发双列瀑布流（图文+短视频混排）：

帖子卡片：作者头像/昵称、封面图、文案摘要（限3行）、位置标签。

关键差异化标签：

🏅 地主认证（已验证本地居民）

📍 这家我吃了10年（本地人情怀）

⏳ 错峰建议（如“上午10点前去不用排队”）

帖子详情页：

顶部图文/视频。

底部两个核心按钮：“👍 本地人觉得有用” 和 “📥 加入我的行程”（一键将碎片地点添加到Tab2路线中，AI自动优化排序）。

发布按钮：右下角“+”发布笔记，可选择是否认证为“本地人推荐”（需通过LBS打卡记录或认证审核）。

4.5 Tab 4：我的（个人）
设计理念：突出视觉化的旅行资产，增加用户离开成本，强化成就感。

页面从上到下布局：

顶部个人信息区：头像、昵称、个人简介、账号绑定（微信/手机号）。

核心数据资产（三列）：足迹城市数 | 收藏路线数 | 社区获赞数。

⭐ 我的足迹地图（视觉重头戏）：

展示中国（或世界）缩略地图，用户去过的城市以发光亮点形式点亮并连线。

点击“查看全部”，进入大屏地图时间轴，滑动查看历史足迹。

功能列表（菜单式）：

📋 我的行程（同步Tab2的已结束行程）

❤️ 收藏夹（收藏的社区帖子/景点/路线）

📝 我的草稿（未发布的社区笔记）

⚙️ 设置（清除缓存、隐私政策、退出登录）



五、数据存储方案（阶段一）
5.1 存储类型与用途
存储类型	用途	阿里云产品
关系型数据	用户、路线、帖子、收藏等结构化数据	MySQL 8.0（安装在ECS上）
缓存数据	用户Session、热点景点数据	Redis（安装在ECS上）
文件存储	用户头像、社区图片、路线封面图	对象存储 OSS
日志存储	应用日志、访问日志	服务器本地文件 + 阿里云日志服务（SLS）
5.2 核心数据表设计（概念层）
模块	核心表	说明
用户	user	用户ID、昵称、头像URL、手机号、微信OpenID、注册时间等
认证	user_session	会话ID、用户ID、过期时间（Redis存储，此表可选）
路线	route	路线ID、用户ID、名称、封面图、天数、总时长、状态（草稿/已保存/已结束）、创建时间
路线-景点	route_scenic	关联ID、路线ID、景点ID、顺序、停留时长、交通建议
景点/POI	scenic	景点ID、名称、经纬度、地址、评分、图片、营业时间、城市编码
社区帖子	post	帖子ID、作者ID、标题、内容、图片列表、城市编码、是否本地人认证、位置标签、创建时间
帖子互动	post_interact	互动ID、帖子ID、用户ID、类型（点赞/收藏/有用）
用户足迹	user_footprint	记录ID、用户ID、景点ID、打卡时间
收藏	favorite	收藏ID、用户ID、目标ID、目标类型（路线/帖子/景点）
5.3 数据库备份策略
自动备份：使用阿里云RDS（或ECS自建MySQL的cron脚本）每日凌晨3:00全量备份

备份留存：保留最近7天的备份文件

异地备份：阶段一可选，阶段二建议实施


六、部署与运维方案
6.1 阶段一部署架构（单机）
text
阿里云ECS（2核4G，Ubuntu 22.04）

6.2 安全与合规
事项	具体措施
ICP备案	为后端域名申请ICP备案（上架必需）
APP备案	在工信部系统为App完成备案（上架必需）
软件著作权	申请软著（华为应用市场硬性要求）
等保/安全评估	如涉及用户生成内容（UGC），准备安全评估报告
服务器安全	修改SSH默认端口、禁用root远程登录、配置防火墙规则
HTTPS	为Nginx配置SSL证书（免费证书如Let's Encrypt）
6.3 监控与告警（阶段二引入）
接入 Prometheus + Grafana 监控服务器CPU、内存、磁盘、网络

配置告警规则：CPU > 80%、内存 > 85%、磁盘 > 80% 时发送告警通知

使用 Spring Boot Actuator 暴露健康检查端点，配合Nginx做健康检测

八、用户核心闭环路径
用户打开App → 主页看到天气和周边推荐。

点击顶部 “✨AI魔法棒” → 输入“广州两天一夜，带长辈” → 生成精细时间轴 → 存入 “已保存”。

行程当天，打开 “行程” 页查看时间轴，逐项打卡。

在景区打开 “社区” ，看到本地人推荐隔壁巷子的老字号，点击 “加入行程” ，AI自动插入行程下午茶时段。

旅行结束，“我的” 足迹地图自动点亮广州，并生成一张“旅行小结海报”供用户分享。
